# wheee — Game Design

## 1. Overview

PvP тактическая игра 1v1 на сетке 7×7.
Игроки одновременно (в тиках) перемещаются и изменяют рельеф.
После серии тиков происходит катаклизм (молния/ветер/дождь).
Цель — заставить соперника погибнуть от катаклизма.

Игра поддерживает зрительский режим с собственными механиками
и роль архитектора, управляющего катаклизмами.

---

## 2. Board

* Размер: 7×7
* Координаты: (x, y), где 0 ≤ x,y < 7
* Высота клетки: `-1 | 0 | +1`

    * `-1` — яма
    * `0` — равнина
    * `+1` — холм
* Начальное состояние: все клетки = 0

---

## 3. Role System

### 3.1 Guest (неавторизован)

* Может сразу нажать «Играть» → попадает в матч как анонимный игрок
* Может авторизоваться → становится Player
* Прогресс/статистика не сохраняются
* Отображается под случайной фамилией из «Войны и мира» (`WAR_AND_PEACE_SURNAMES` в `@wheee/shared`) и случайным флагом (или флагом по геолокации/Accept-Language)

### 3.2 Player (авторизован)

* Выбирает 1 из 3 персонажей (см. §4)
* Нажимает «Играть» → система автоматически подбирает пару (chatroulette-стиль)
* Может переключиться в режим наблюдателя
* Сохраняется статистика, рейтинг, история матчей

### 3.3 Watcher / Наблюдатель

* Переходит в режим через кнопку «Наблюдать» или по прямой ссылке на матч
* Система автоматически назначает на активный матч
* По окончании матча автоматически перекидывается на другой начавшийся матч (авто-ротация)
* Имеет собственные механики и челленджи (не влияют на ход игры игроков):
    * **Predict Winner** — в фазе прогноза предсказать, кто выиграет раунд → +10 очков, если в этот катаклизм погиб именно предсказанный проигравшим соперник
    * **Predict Move** — предсказать ход конкретного игрока в тике → +5 очков за точное совпадение
    * **Break Instruments** — раз за матч может «сломать» один прибор прогноза (флюгер или барометр); поломка действует на **обоих** игроков до конца раунда (см. §11.3)
* Очки авторизованных наблюдателей копятся в лидерборде watchers

### 3.4 Architect (особая роль)

* Управляет катаклизмами матча: вручную выставляет тип погоды и направление ветра
* Вместо рандома — ручной выбор перед каждым раундом (окно решения `ARCHITECT_DECISION_MS` = 8 с; если не ответил — игра продолжается со случайной погодой)
* Может размещать бонусные точки на карте (см. §10), 1 бонус за раунд
* Видит полное состояние игры (оба игрока, все высоты)
* Максимум 1 архитектор на матч

### 3.5 Bot (системный игрок)

* Если игрок ждёт в очереди дольше `BOT_MATCH_DELAY_MS` (по умолчанию 30 с) — матч создаётся с ботом
* Бот играет каноническим состоянием на стороне своего игрока (`engine/bot.ts`). Он не содержит
  собственной копии правил: каждое допустимое действие проигрывается через `applyTick`, после чего
  на результат обрушивается настоящий катаклизм (`resolveLightning` / `resolveWind` / `resolveRain`) для каждой погоды,
  которую ещё допускает прогноз. Порядок предпочтений:
  1. Доля погод, которые бот переживает
  2. Доля погод, которые уносят оппонента (только если `hunt`)
  3. Ближе к центру — так равные по безопасности ходы не выглядят случайными
* Прогноз бот читает как игрок: сломанный наблюдателем флюгер возвращает его к защите от всех четырёх
  направлений, сломанный барометр — к защите и от дождя, и от его отсутствия. Пустой флюгер при целом
  приборе означает штиль (архитектор может заказать дождь без ветра). Молнию бот учит бесплатно:
  прогноз даёт ещё одну ось (сломанный барометр — защита от всех комбинаций дождя и молнии),
  и настоящий `resolveLightning` сам объясняет ему громоотводы и подкопы
* Сила задаётся `BotStrength`: `BOT_MATCH` (`skip` 4%, `blunder` 12%, охотится) и `BOT_PRACTICE`
  (`skip` 8%, `blunder` 35%, не охотится) — в туториале бот заботится только о себе, новичок проигрывает
  погоде, а не ловушке
* Отвечает с человекоподобной задержкой 1–4 с, получает случайное имя/флаг как гость
* Одно решение — доли миллисекунды (~107 действий × до 16 погод), считается синхронно в такте комнаты

## 4. Characters

Авторизованный игрок выбирает одного из 3 персонажей-культур:

| Персонаж | Культура | Визуал |
|----------|----------|--------|
| 🌾 Wheat | Пшеница | Золотистое пламя / колосья |
| 🌾 Rice | Рис | Зелёное пламя / ростки |
| 🌽 Corn | Кукуруза | Оранжевое пламя / початки |

В MVP персонажи отличаются **только визуально** (модель + палитра бабочек §5.2).
В будущем могут появиться уникальные пассивные способности.

## 5. Players

* Количество: 2 (A и B)
* Начальная позиция: случайная из пула симметричных пар (зеркально относительно центра 3,3):
    * `(3,5) / (3,1)` — вертикаль, расстояние 4
    * `(1,3) / (5,3)` — горизонталь, расстояние 4
    * `(2,4) / (4,2)` — диагональ, расстояние ~2.8
    * `(4,4) / (2,2)` — обратная диагональ, расстояние ~2.8
* Игрок занимает 1 клетку
* Высота игрока = высоте клетки

### 5.1 Two-Sided Map

Оба игрока играют на одной карте, но на **разных сторонах** плитки:

* Player A видит верхнюю поверхность, Player B — нижнюю
* Каждый игрок **всегда видит себя сверху**, а оппонента — на обратной стороне
* Клиент не знает, какой он игрок (A или B) — сервер отправляет уже трансформированное состояние
* Для Player B сервер **инвертирует высоты** (negateBoard) и **инвертирует действия** (raise ↔ lower)
* Результат: когда любой игрок нажимает «Raise», на его стороне появляется холм, а у оппонента — яма

### 5.2 Присутствие соперника

Соперник стоит на дальней грани плиты и с обычного ракурса не виден. Чтобы игрок
всё же чувствовал, *где* тот находится, над клеткой соперника (на своей стороне
доски) кружат **три бабочки с крыльями из полупрозрачных камней**
(`packages/client/src/lib/insects.ts`):

* у каждого персонажа свой вид и цвет — рой заодно подсказывает, кого вы встретили
* размер и прозрачность сдержанные (`SPRITE_SIZE ≈ 1`, opacity ≈ 0.7): намёк, а не
  конкурент основному геймплею
* крылья бьются четырьмя кадрами атласа со вспышкой грани на сложенном крыле
* во время катаклизма рой **разлетается**; после — снова собирается над клеткой
* земля и геометрия плиты не трогаются — только спрайты над клеткой

Это не заменяет флип и не раскрывает действия соперника: видно только место.

### 5.3 «Это ты»

У гостя и у соперника одинаковые случайные фамилии из «Войны и мира», поэтому
игрок может не понять, какой из двух персонажей его. На своей плашке имя
дополняется суффиксом `(You)` / `(Вы)` (`hud.you` в i18n), а кольцо под своим
персонажем ярче и показывается только когда есть локальный игрок (в лобби и у
зрителя кольца нет).

## 6. Time System (Ticks)

* `TICK_DURATION_MS`: 6000 (6 секунд)
* `TICKS_PER_ROUND`: 5
* Показ прогноза: `FORECAST_DISPLAY_MS` = 3 с (или 8 с, если в матче архитектор)
* Показ катаклизма перед следующим раундом: `WEATHER_DISPLAY_MS` = 4 с

Цикл:

1. Forecast (3–8 с)
2. Tick ×5 (по 6 с; тик завершается досрочно, если оба игрока сдали действие)
3. Weather (катаклизм)
4. Если никто не погиб — новый раунд

---

## 7. Actions (1 action per tick)

Если игрок не сделал действие — оно сгорает.

### 7.1 Move

* Направления: N, S, E, W, NE, NW, SE, SW (8 направлений, как король в шахматах)
* Смещение на 1 клетку
* Нельзя выйти за карту

### 7.2 Raise

* `height += 1`
* Ограничение: максимум +1

### 7.3 Lower

* `height -= 1`
* Ограничение: минимум -1

---

## 8. Terrain Rules

* Можно изменять **любую** клетку, включая занятую игроком

---

## 9. Simultaneity

* Все действия применяются **одновременно в конце тика**
* Конфликты:

    * Raise + Lower → нет изменения
    * Move в одну клетку → оба могут стоять вместе

---

## 10. Sponsor / Challenge Bonuses

Бонусные точки на карте. Принцип: **максимально нейтральные, не влияют на баланс.**

Размещает: Architect (или система автоматически).

### 10.1 Trigger

* Бонус активируется, когда игрок **оказывается** на конкретной клетке

### 10.2 Типы бонусов

| Бонус | Эффект |
|-------|--------|
| Time Extend | +2 секунды к текущему тику (только для этого игрока) |
| Intel | Показать, что выбрал противник в текущем тике (после того как оба сделали ход) |
| Clear Sky | Убрать неопределённость прогноза на 1 раунд |

> **Статус реализации:** размещение и подбор реализованы (engine возвращает
> `activatedBonus` в `TickResult`, бонус снимается с карты). Сами **эффекты**
> (Time Extend / Intel / Clear Sky) не применяются и применяться не будут: дать
> игроку Intel или Clear Sky — значит продать преимущество. Ящик работает иначе,
> см. §10.4: ценен сам факт подбора, а не тип бонуса.

### 10.3 Ограничения

* Максимум 1 бонус на карте одновременно
* Бонус не размещается на клетке, где стоит живой игрок
* Если оба игрока одновременно встали на неадресованный бонус — он исчезает без активации
* Не влияет на механики ветра/дождя/смерти

### 10.4 Ящик и значок серии

Ящик — вход в косметическую систему значков. Игрового эффекта у него нет, поэтому
и вопроса о честности не возникает: он не даёт преимущества, он **начинает счёт**.

**Кому достаётся.** Ящик кладётся, если серии нет хотя бы у одного игрока, и
дальше всё зависит от того, скольким он нужен:

| У кого нет серии | Ящик |
|---|---|
| У обоих | **общий** (`for` не задан) — гонка, чей ход первым приведёт на клетку. Если пришли оба разом, ящик сгорает впустую |
| Только у одного | **адресован** ему (`BonusCell.for`); игрок со значком проходит по клетке насквозь, ящик остаётся лежать |
| Ни у кого | не появляется |

Адресность нужна ровно для одного: чтобы игрок со значком не мог наступить на
клетку назло и лишить новичка входа в систему. Когда значка нет у обоих, охранять
не от кого, и запирать камень за одним из них было бы несправедливо.

Цена подбора честная в любом случае: ход, потраченный на переход к клетке, — это
ход, не потраченный на спасение от бури.

Ящик не появляется в туториале и когда в матче есть архитектор — там бонусы
раскладывает он.

**Лестница.** Значок показывает ступень, число — точный счёт:

| Серия | 1–2 | 3–5 | 6–9 | 10–19 | 20–49 | 50+ |
|-------|-----|-----|-----|-------|-------|-----|
| Значок | 🍃 | 💨 | 🌧 | ⛈ | 🌪 | 🌀 |

**Жизненный цикл.**

| Событие | Что происходит |
|---|---|
| Подобрал ящик | серия = 1 |
| Победа | +1 |
| Ничья | без изменений — слишком редка и слишком симметрична |
| Поражение | обнуление; на экране итога предлагается вернуть значок за просмотр рекламы |
| Поражение по обрыву связи | без изменений — это вина сети, а не игрока |

Спасение одно на серию. Обнуление происходит **сразу**, а реклама возвращает
значок обратно: если откладывать потерю до ухода с экрана, закрытая вкладка
становилась бы бесплатным спасением.

**Где живёт.** Серия хранится на клиенте (`lib/streak.ts` поверх `lib/storage.ts`),
то есть переживает перезагрузку и работает у анонимных игроков — на GameDistribution
в том числе, где серверного аккаунта нет вовсе. Сервер серию не считает и не
проверяет: он принимает число при входе в очередь и раздаёт его сопернику в
`PlayerInfo.streak`, чтобы оба экрана рисовали одинаковую плашку. Подделать значок
можно, но он косметический — обман видит только его владелец.

**На плашке.** До третьей ступени рядом с флагом, с третьей — вместо него, чтобы
плашка не разбухала (§5.3).

## 11. Player HUD / Forecast Instruments

Каждый игрок видит в углу экрана:

### 11.1 Wind Vane (Флюгер)

* Показывает **предполагаемое направление** будущего ветра
* Если направлений-кандидатов два — флюгер анимированно мечется между ними
* Если ветра не будет — флюгер неподвижен, приспущен

### 11.2 Barometer (Барометр)

Прибор один, сигналов два: пиктограмма в центре и обод вокруг неё.

* Лестница пиктограммы по вероятности дождя — и она **заканчивается на дожде**:
    * ☀️ — нет дождя
    * 🌤 — маловероятен
    * ⛅ — возможен
    * 🌧 — вероятен

* Разряд на пиктограмме рисует только молния (`lightningProbability ≥ 0.5`):
    * 🌩 — гроза без дождя
    * ⛈ — гроза с дождём

  Поэтому разряд на приборе всегда значит именно молнию, а не «очень сильный дождь».

* **Наэлектризованный обод** — вероятность молнии рисуется дугами статики по внешнему
  кольцу циферблата: одна случайная искра при 0.25, ровный треск при 0.75, обод в
  фиолетово-синем свечении при 1.0. Пиктограмма отвечает «что может случиться», обод —
  «насколько это близко»
* **Стрелка не трогается** — она уже кодирует направления ветра, второго сигнала на ней нет

### 11.3 Breaking Instruments

* Наблюдатель (Watcher) может 1 раз за матч «сломать» один инструмент (флюгер или барометр)
* Поломка применяется **обоим игрокам сразу** (реализация в `Room.watcherBreakInstrument`)
* Сломанный прибор показывает хаотичные данные; флаг сбрасывается при генерации нового прогноза в следующем раунде
* Приборов по-прежнему два, но сломанный барометр теперь слепит **всё небо**: и дождь,
  и молния читаются как хаос (пиктограмма мигает, обод искрит случайно). Флюгер остаётся
  только про ветер

## 12. Weather System

Стихий три — ветер, дождь, молния — и тип катаклизма это просто их набор:
`wind | rain | wind_rain | lightning | wind_lightning | rain_lightning | wind_rain_lightning`.
Читать тип напрямую не надо, для этого есть предикаты `hasWind` / `hasRain` /
`hasLightning` в `@wheee/shared`.

Случайная генерация (`randomWeatherDecision(round)`) берёт смесь **из таблицы по
номеру раунда** — `WEATHER_SCHEDULE` в `packages/shared/src/constants.ts`, единственное
место для подкрутки весов:

| Раунды | Смесь |
|---|---|
| 1–2 | ветер 55% / ветер+дождь 45% |
| 3–4 | ветер 40% / ветер+дождь 35% / ветер+молния 15% / молния 10% |
| 5–6 | ветер 25% / ветер+дождь 25% / ветер+молния 25% / ветер+дождь+молния 15% / молния 10% |
| 7+ | ветер+дождь+молния 40% / ветер+молния 30% / ветер+дождь 20% / молния 10% |

Три вывода из таблицы:

* **В раундах 1–2 молнии нет вообще** — новичок учит ровно ту погоду, что была вчера
* **Дальше буря нарастает**, и партия обязана закончиться: поздний туртлинг
  («подними стену и стой») ломается сам, без сужающейся доски — эскалация играет
  её роль, не отнимая у игрока клетки
* **Чистая молния** даёт генерации первый катаклизм **без ветра**: гула нет, только
  треск на приборе. Раньше ветер дул в каждом случайном катаклизме

Если есть Architect — он выбирает тип и направление вручную, включая типы, которые
случайная генерация не выдаёт (`rain`, `rain_lightning`): движок их поддерживает.

**Порядок внутри катаклизма: молния, потом ветер, потом дождь.** Молния судит позиции
ровно такими, какими они были в конце пятого тика, — любая её смерть объяснима одним
кадром. Ветер не поднимает, он только сбрасывает в ямы и прижимает к стенам, так что
после ветра разряд почти никогда бы не находил цель. Дождь считает низины уже по новым
позициям после ветра — то есть ветер может столкнуть в низину, которую тут же затопит.
Драматургия совпадает с физикой: вспышка, потом порыв, потом ливень.

**Буря обрывается на первой смерти.** Если молния кого-то забрала, раунд уже решён:
ни ветра, ни дождя. Если забрал ветер — дождя нет вообще. Раньше выживший после ветра
мог утонуть в том же катаклизме, и раунд заканчивался ничьей при живом победителе.
Смерть всегда заканчивает матч, поэтому пропущенные стихии бывают только в последнем
катаклизме партии.

Тот же принцип действует внутри каждой стихии: разряд один и уходит в одну сторону
(§15), ветер стихает, когда кого-то унесло за край (§13.2), вода перестаёт подниматься,
когда кто-то ушёл под неё (§14.4). Итого **буря забирает не больше одного игрока**,
а ничья остаётся возможной только при полной симметрии — равные макушки, равный разбег
или равный объём.

## 13. Wind

### 13.1 Direction

* N→S, S→N, E→W, W→E

### 13.2 Rules (для каждого игрока)

Высоты вычисляются с учётом стороны игрока (Player B видит инвертированные высоты).

1. **Проверка укрытия (upwind scan):**

    * Сканируем **против ветра** от позиции игрока до края карты
    * Если любая клетка по этому пути **выше** игрока → ветер полностью заблокирован (игрок укрыт)

2. Если не укрыт — игрок **сносится по ветру** (downwind push):

    * двигается клетка за клеткой

3. При движении:

    * если следующая клетка **выше** текущей → остановка перед ней (стена)
    * если **ниже** текущей → игрок падает в яму и останавливается (стенка ямы блокирует)
    * если равна → продолжает

4. Если достигнут край карты:

    * игрок погибает (сдувает с карты)

5. **Тай-брейк по разбегу** — если ветер уносит с карты **обоих**:

    * **разбег** = число клеток, которые игрок проходит по полю до вылета (погибнуть можно только когда все клетки по ветру равны по высоте, поэтому разбег = расстояние до подветренного края)
    * гибнет тот, у кого разбег **короче**
    * буря стихает в момент его вылета, поэтому второй смещается ровно на столько шагов, сколько успел сделать погибший, и **выживает**
    * если разбеги **равны** — гибнут оба
    * при обычном катаклизме, где гибнет только один, снос второго не обрезается

## 14. Rain

### 14.1 Basin Detection

* Низина = область клеток, окружённых клетками строго выше или краем карты
* Край карты считается стеной
* Бассейны вычисляются **отдельно для каждого игрока** с учётом его стороны карты (Player B видит инвертированные высоты)

### 14.2 Water Fill

* Вода заполняет **минимальный уровень** в каждой низине
* Все низины наливаются с одной скоростью **по объёму**: низине из `n` клеток нужно
  в `n` раз больше времени, чем одиночной ямке
* `waterVolume` — сколько воды успело выпасть, в «клетко-глубинах»; низина из `n`
  клеток стоит на `min(1, waterVolume / n)` своей глубины. Клиент рисует уровень
  ровно по этому числу, поэтому недолитые низины видны как есть

### 14.3 Death

* Игрок погибает, если стоит на клетке с минимальным уровнем **своего** бассейна
* На клиенте утопший **не исчезает**: он остаётся стоять в залитой низине (сквозь
  полупрозрачную воду и, если катаклизм решающий, сквозь стеклянную плиту §16.1).
  Снос ветром уносит тело с карты; вода — нет. Причину смерти объясняет экран итога

### 14.4 Тай-брейк по объёму

Если в воде оказались **оба** игрока:

* **объём** = площадь бассейна в клетках; чем теснее яма, тем быстрее она наполняется
* гибнет тот, чей бассейн **меньше**
* вода перестаёт подниматься в момент его смерти (`waterVolume` = объём погубившей низины), поэтому широкая низина не успевает налиться и её хозяин **выживает** — он видит, как вода поднялась до `меньший объём / его объём` глубины и замерла
* если объёмы **равны** — гибнут оба

Правило не постулируется, а **выводится** из §14.2: игрок сам видит, как его низина
наливается медленнее, и насколько близко было. Чем ближе объёмы, тем выше успела
подняться вода у выжившего.

Это зеркало тай-брейка по разбегу (§13.2): в обоих катаклизмах считаются клетки, и
у кого их меньше — тот гибнет первым.

Примеры:

* Игрок в `-1`, вокруг `0` → смерть
* Игрок в `0`, вокруг `+1` → смерть
* Игрок в `0`, но есть `-1` рядом → выживает

## 15. Lightning

Ветер забирает открытых, дождь — низких, молния — высоких. До третьей стихии в
позиционной таблице была дырка: стоять на `+1` почти бесплатно — ветер сбрасывает с
холма на соседнюю клетку и стихает, вода до тебя не доходит.

### 15.1 Правило

У персонажа есть **макушка**: `CROWN_HEIGHT` = +0.5 над той клеткой, на которой он
стоит. Молния считается **отдельно для каждой стороны** (Player B видит инвертированные
высоты), как ветер и дождь.

> Игрок — цель разряда, если **ни одна клетка его стороны не выше его макушки**
> (высота клетки + 0.5). Любая строго более высокая клетка где угодно на стороне —
> **громоотвод**: разряд уходит в неё, игрок жив.

Всё остальное выводится из этой одной фразы:

* **Холм — эшафот.** На `+1` макушка на `1.5`, выше не бывает ни одной клетки.
  Под грозовым прогнозом холм — смерть, которую не отменит никакой громоотвод
* **Яма заземлена.** На `-1` макушка на `-0.5`, её перебивает любой ноль на стороне.
  Ямы молниебезопасны — они остаются добычей дождя
* **Ровное поле убивает.** Все клетки на одном уровне (все `0` **или** все `-1` —
  правило относительное, глобальным копанием его не обмануть) оставляют игрока самым
  высоким предметом в степи
* **Громоотвод строится**, как и стена от ветра: поднять клетку, на которой ты **не**
  стоишь. Соперник сносит единственный громоотвод одним действием, поэтому запас
  громоотводов стоит тиков — в этом вся экономика
* **Подкоп на пятом тике — подпись стихии.** Соперник опускает клетку под тобой (на
  твоей стороне она вздувается в `+1`) → макушка перебивает все громоотводы. На тиках
  1–4 это дуэль (сойди или подкопай обратно), на пятом ответа нет. Тот же подкоп уже
  существует для дождя (толчок в яму), так что это заточка старого приёма, а не новая
  патология
* **Сквозная текстура:** каждый мой громоотвод — яма на стороне соперника. Моя защита
  от молнии копает ему ловушки для дождя. Новых правил не нужно

Куда именно бьёт разряд при нескольких одинаково высоких громоотводах: ближайший к
игроку, при равенстве — с меньшими `(y, x)`. Это не геймплей, а детерминизм для реплеев.

### 15.2 Оба открыты — тай-брейк по превышению

Разряд один. Если открыты оба, он выбирает того, кто **сильнее торчит над своим
собственным миром**:

* **превышение** = макушка − самая высокая из **остальных** клеток своей стороны
* гибнет тот, у кого превышение **больше**; второго разряд проходит мимо
  (`lightningSpared`), и его `boltCell` пуст — гром ушёл на другую сторону, у него
  ничего не поглощало
* если превышения **равны** — гибнут оба, ничья: это симметрия того же вида, что равный
  разбег (§13.2) и равный объём (§14.4)

Превышение относительно, как и сама открытость: ровно опустить всю свою сторону —
ничего не изменить. Сравнение абсолютных высот макушек было отвергнуто именно поэтому:
оно отдавало любой обоюдный тай-брейк тому, кто копает глобально, — ровно тот эксплойт,
против которого правило и относительно.

Смешанных двойных смертей не бывает: как и у других стихий, буря обрывается на первой
смерти (§12).

### 15.3 Что видит игрок

* Хореография внутри `WEATHER_DISPLAY_MS`: тишина (небо темнеет, ветер замирает, звук
  падает) → два тусклых свечения в облаках → **УДАР** (лента разряда + локальный свет +
  гром + вибрация) → два слабых повторных разряда → дальше ветер и дождь, если буря
  не кончилась
* **Полноэкранной вспышки нет никогда** — только локальный свет в точке удара
  (светочувствительность: максимум 3 маленькие вспышки за ~1.2 с)
* **Нет ни гари, ни обугливания.** Смерть от молнии яркая, а не сожжённая: короткая
  белая вспышка на монолите, бабочки разлетаются, экран итога называет причину
* **Поглощённый разряд рисуется всегда**: буря была, игрок жив → видно, как разряд
  нырнул в холм-громоотвод. Это и есть весь туториал фичи — игрок **видит**, что его
  спасло
* Решающий разряд на дальней стороне читается сквозь стеклянную плиту (§16.1)

### 15.4 Обратная совместимость: capability handshake

GamePush-порталы обновляются асинхронно (модерация, кэш зипа), пока wheee.io/api
раскатывается мгновенно — старый клиент может оказаться на новом сервере. Поэтому
гроза включается в матче только когда оба клиента объявили поддержку (`caps` при
входе в очередь); старые портальные билды играют по прежним правилам, пока не
обновятся. Без объявленной поддержки погодный график зажат на уровень раундов 1–2
(только `wind`/`wind_rain`), а заказ архитектора с молнией сводится к базовому типу —
тот же механизм, которым уже зажат туториал.

## 16. Win / Lose

Игрок проигрывает, если:

* его сдуло за карту (wind)
* он утонул (rain)
* его нашла молния — он был самой высокой точкой своей стороны (lightning, §15)
* он отключился и не вернулся за grace-период (`RECONNECT_GRACE_MS` = 30 с) — победа оппоненту (forfeit, `deathCause: disconnect`)

Если оба погибли в один катаклизм — ничья (draw). Но буря забирает не больше одного: обоюдный снос разводит тай-брейк по разбегу (§13.2), обоюдное утопление — тай-брейк по объёму (§14.4), а смешанной смерти «одного сдуло, другой утонул» не бывает вовсе, потому что буря обрывается на первой смерти (§12). Так что ничья остаётся возможной только при полной симметрии: равный разбег или равный объём.

### 16.1 Стеклянная плита

Оба тай-брейка решаются сравнением двух половин, а соперник стоит на дальней
грани — то есть решающее событие происходит вне поля зрения. Поэтому катаклизм,
в котором **кто-то погиб**, делает всю плиту полупрозрачной: оба персонажа видны
одновременно, и игрок сам видит, кто вылетел за край первым и чью низину вода
закрыла раньше.

Реализация (`packages/client/src/lib/glass.ts`): opacity ≈ 0.5, нефритовое
свечение (`emissive`), линии сетки остаются читаемыми. Порядок отрисовки лиц
плиты и обеих вод задаёт `GLASS_ORDER`, иначе дальняя грань и вода соперника
не видны сквозь ближнюю.

Плита проясняется только **после** того, как буря разрешилась (клиент получает
`weather:result` со списком смертей до начала анимации), поэтому о намерениях
соперника не утекает ничего — виден только результат. Информации это не
добавляет и в остальном: доску всегда можно осмотреть с другой стороны кнопкой
флипа (§2).

### 16.2 Кадр на узких экранах

На портретных и узких экранах (`aspect < 1.2`) камера отодвигается так, чтобы
вся плита попадала в кадр (`fitCameraToBoard` в `App.vue`). На широких экранах
кадр остаётся прежним плотным — подгонка не трогает десктопный вид.

## 17. Core Gameplay Loop

Повторяется до победы:

1. Architect выставляет (или система генерирует) катаклизм
2. Игроки видят прогноз (Forecast Instruments)
3. 5 тиков:

    * каждый тик: 1 действие
    * Watcher может предсказывать ходы / результат
4. Катаклизм (визуализация ветра / дождя / потопа)
5. Проверка смерти
6. Если никто не погиб — следующий раунд

## 18. Matchmaking

* **Play**: нажал «Играть» → попал в очередь → система подбирает пару → матч начинается.
  Если пара не нашлась за `BOT_MATCH_DELAY_MS` (30 с) — матч с ботом (см. §3.5)
* **Watch**: нажал «Наблюдать» → назначается на первый активный матч → авто-ротация после финиша (`watcher:redirect`).
  Кнопка показывается только авторизованным (очки идут в таблицу зрителей) и только когда `lobby:status.liveMatches > 0`
* **Architect**: назначается на активный матч (макс 1 на комнату); если активных матчей нет — `architect:no_match`.
  Роль скрыта из лобби (`SHOW_ARCHITECT = false` в `LobbyOverlay.vue`) — протокол и сервер работают, входа для игрока нет

### 18.1 Reconnect

* При `game:start` игрок получает `reconnectToken`
* При обрыве WS у игрока есть `RECONNECT_GRACE_MS` (30 с) на возврат; все таймеры матча ставятся на паузу, оппонент видит «opponent disconnected»
* Возврат по токену → `reconnect:ok` с полным состоянием; истечение grace → forfeit

## 19. Design Principles

* Простые правила → сложные ситуации
* Нет мгновенных гарантированных убийств
* Last-tick действия = mindgame, не exploit
* Игрок всегда имеет шанс спастись (move)
* Наблюдатель вовлечён, но не ломает баланс
* Server-authoritative: вся истина на сервере

## 20. Scope

В игре нет (осознанно):

* высот > +1 / < -1
* особых клеток
* уникальных способностей персонажей
* мульти-юнитов
* эффектов бонусов — сознательно: ящик даёт значок, а не преимущество (§10.4)

Реализовано:

* 8-directional movement (как король в шахматах)
* Изменение ландшафта под игроком
* Two-sided map (серверная инверсия для Player B)
* Присутствие соперника: бабочки с каменными крыльями над его клеткой (§5.2)
* Метка локального игрока: `(You)` / `(Вы)` на плашке + кольцо (§5.3)
* Погода по таблице раундов `WEATHER_SCHEDULE` (§12): в раундах 1–2 только ветер и ветер+дождь,
  дальше подмешивается молния — вплоть до катаклизма без ветра вообще
* Upwind shielding (укрытие за возвышенностью)
* Wind push animation (игрока сносит визуально)
* Молния бьёт в самую высокую точку стороны; громоотводы, подкоп на пятом тике (§15)
* Тай-брейк по разбегу (§13.2), по объёму низины (§14.4), по превышению макушки (§15.2)
* Буря обрывается на первой смерти: после смертельного разряда нет ни ветра, ни дождя (§12)
* Пропорциональное заполнение низин по `waterVolume`; утопший остаётся в воде
* Стеклянная плита на решающем катаклизме (§16.1); кадр на узких экранах (§16.2)
* Action preview (превью raise/lower/move перед подтверждением тика)
* Guest/Player/Watcher/Architect роли + бот (поиск через настоящий катаклизм)
* Ящик на карте и косметический значок серии на плашке; реклама возвращает потерянный значок (§10.4)
* Авторизация: Google/GitHub OAuth, Telegram Mini App, Yandex Games, GamePush
* Matchmaking (автоподбор пары + бот-фоллбек)
* Серверный game engine + reconnect + rate limiting
* WebSocket real-time sync
* Forecast instruments (флюгер + барометр с наэлектризованным ободом §11.2) + поломка наблюдателем
* Watcher mode (наблюдение + предсказания + очки); кнопка Watch — только авторизованным при `liveMatches > 0`
* Architect mode (ручная погода + бонусы); вход из лобби скрыт (`SHOW_ARCHITECT = false`)
* Реплеи (снапшоты состояний, просмотр из лобби)
* Лидерборды (players / watchers), история матчей
* Мультиплатформенность: web, Telegram Mini App, Yandex Games, GamePush
* i18n (en/ru), звук (Howler), мобильный ввод
* Интерактивный туториал (practice-матч vs бот без охоты)

## 24. Data Structures (`@wheee/shared`)

Актуальный источник истины — `packages/shared/src/types.ts`. Ключевые типы:

```ts
type Height = -1 | 0 | 1

type Cell = { height: Height; bonus: BonusType | null }

type CharacterType = 'wheat' | 'rice' | 'corn'

type Player = {
  id: 'A' | 'B'
  x: number
  y: number
  character: CharacterType
  alive: boolean
}

type Role = 'guest' | 'player' | 'watcher' | 'architect'

type GamePhase = 'waiting' | 'forecast' | 'ticking' | 'weather' | 'finished'

type ForecastData = {
  windCandidates: WindDir[]      // 1-2 направления (реальное — среди них), пусто без ветра
  rainProbability: number        // 0 | 0.25 | 0.75 | 1.0
  lightningProbability: number   // 0 | 0.25 | 0.75 | 1.0 — обод барометра (§11.2)
  instrumentsBroken: Record<'A' | 'B', { vane: boolean; barometer: boolean }>
}

type BonusType = 'time_extend' | 'intel' | 'clear_sky'

type GameState = {
  board: Cell[][]
  players: Record<'A' | 'B', Player>
  tick: number
  round: number
  phase: GamePhase
  forecast: ForecastData
  activeBonus: BonusCell | null
  weather: { type: WeatherType; dir: WindDir } | null
  winner: 'A' | 'B' | 'draw' | null
}

type DeathCause =
  | { type: 'wind'; dir: WindDir }
  | { type: 'rain' }
  | { type: 'lightning' }
  | { type: 'disconnect' }

type WeatherResult = {
  state: GameState
  deaths: PlayerId[]
  deathCauses: Partial<Record<PlayerId, DeathCause>>
  windPath: Record<PlayerId, { x: number; y: number }[]>
  windSpared: PlayerId | null                 // кого буря отпустила по тай-брейку разбега (§13.2)
  floodedCells: { x: number; y: number }[]    // сторона A (для B сервер подменяет на его сторону)
  floodedCellsB: { x: number; y: number }[]
  rainSpared: PlayerId | null                 // кого отпустила вода по тай-брейку объёма (§14.4)
  waterVolume: number                         // сколько воды выпало, в клетко-глубинах (§14.2); 0 — дождя не было
  boltCell: Record<PlayerId, { x: number; y: number } | null>  // куда ударил разряд на каждой стороне:
                                              // клетка игрока при смерти, громоотвод при поглощении, null — не бил (§15)
  lightningSpared: PlayerId | null            // кого разряд прошёл мимо по тай-брейку превышения (§15.2)
}

type WatcherState = {
  score: number                 // +10 за угаданного победителя, +5 за угаданный ход
  predictions: WatcherPrediction[]
  breakUsed: boolean
}
```

WS-протокол (все `ClientMessage` / `ServerMessage`) описан в `packages/shared/src/protocol.ts`.
`lobby:status` несёт `online`, `inQueue` и `liveMatches` (число активных не-practice комнат,
на которые можно посадить зрителя) — см. §18.
